2. Use Case Scenarios

UC-01: Register Account

FieldDescription
Use Case IDUC-01
Primary ActorJob Seeker
PreconditionUser is not registered in the system.
PostconditionUser account is created and stored in the PostgreSQL database.
TriggerUser navigates to the registration page.

Main Success Scenario

  1. User opens the ResumeLens AI web application.
  2. User clicks "Register" and enters email and password.
  3. System validates the email format and password strength (min 8 characters).
  4. System hashes the password using bcrypt.
  5. System stores the new candidate record in the candidates table.
  6. System returns a success message with HTTP 201 status.

Alternative Flows

  • 3a. Email already registered → System returns HTTP 409 "Email already exists."
  • 3b. Invalid email format → System returns HTTP 422 validation error.
  • 3c. Password too short → System returns HTTP 422 "Password must be at least 8 characters."

UC-03: Upload Resume (PDF)

FieldDescription
Use Case IDUC-03
Primary ActorJob Seeker
PreconditionUser is logged in with a valid JWT token.
PostconditionResume PDF is saved on the server and text is extracted via NLP.
TriggerUser clicks "Upload Resume" on the dashboard.

Main Success Scenario

  1. User selects a PDF file from their computer.
  2. System validates the file type (must be .pdf) and size (< 10 MB).
  3. System saves the PDF to the /uploads/ directory using aiofiles.
  4. System extracts raw text from the PDF using pdfplumber.
  5. System uses spaCy NLP to extract skills, experience, and education sections.
  6. System generates a 384-dimensional embedding vector using Sentence-BERT.
  7. System stores the resume metadata, extracted text, and embedding in PostgreSQL (with pgvector).
  8. System returns the resume ID and extracted summary with HTTP 201.

Alternative Flows

  • 2a. File is not a PDF → System returns HTTP 400 "Only PDF files are accepted."
  • 2b. File exceeds 10 MB → System returns HTTP 413 "File too large."
  • 4a. PDF is image-based (scanned) → System uses OCR (pytesseract) as a fallback.

UC-05: View Match Score

FieldDescription
Use Case IDUC-05
Primary ActorJob Seeker
PreconditionResume and Job Description have been submitted.
PostconditionMatch scores (dense, sparse, hybrid) are displayed on the dashboard.
TriggerUser clicks "Analyze Match" after providing both inputs.

Main Success Scenario

  1. User clicks "Analyze Match" on the React Dashboard.
  2. Frontend sends a POST request to /matches/evaluate endpoint.
  3. FastAPI dispatches the heavy computation to a Celery worker via Redis.
  4. Celery worker computes the Dense Score (cosine similarity of SBERT vectors).
  5. Celery worker computes the Sparse Score (BM25 keyword ranking).
  6. System calculates the Hybrid Score: 0.6 × dense + 0.4 × sparse.
  7. Results are saved to the match_evaluations table in PostgreSQL.
  8. React Dashboard renders the scores as interactive bar charts using Recharts.

Alternative Flows

  • 3a. Celery worker is offline → System returns HTTP 503 "Service temporarily unavailable."
  • 4a. Resume text is empty → Dense score defaults to 0.0.

UC-06: View Skill Gap Analysis

FieldDescription
Use Case IDUC-06
Primary ActorJob Seeker
PreconditionMatch evaluation has been computed (UC-05 completed).
PostconditionPersonalized skill gap feedback is displayed on the dashboard.
TriggerSystem automatically generates feedback after match scoring.

Main Success Scenario

  1. After match scoring completes, system sends the resume text and job description to Google Gemini LLM.
  2. Gemini API analyzes the gap between the candidate's skills and job requirements.
  3. LLM returns a structured JSON response with: skill name, current level, required level, severity, and recommended resources.
  4. System validates the LLM response using Pydantic schemas.
  5. Skill gap data is stored in the database.
  6. React Dashboard renders skill gap cards with severity indicators (High / Medium / Low).

Alternative Flows

  • 1a. Gemini API is rate-limited → System returns cached/empty feedback with a warning.
  • 3a. LLM returns malformed JSON → System falls back to empty skill gap list.

UC-02: Login

FieldDescription
Use Case IDUC-02
Primary ActorJob Seeker
PreconditionUser has a registered account (UC-01 completed).
PostconditionUser receives a JWT access token for authenticated API access.

Main Success Scenario

  1. User enters email and password on the login form.
  2. System retrieves the user record from the database.
  3. System verifies the password against the stored bcrypt hash using passlib.
  4. System generates a JWT token (signed with HS256, valid for 60 minutes).
  5. System returns the token to the client with HTTP 200.

Alternative Flows

  • 2a. Email not found → System returns HTTP 401 "Invalid credentials."
  • 3a. Wrong password → System returns HTTP 401 "Invalid credentials."

UC-04: Enter Job Description

FieldDescription
Use Case IDUC-04
Primary ActorJob Seeker
PreconditionUser is logged in.
PostconditionJob description text and its embedding vector are stored in the database.

Main Success Scenario

  1. User pastes the full job description text into the textarea on the dashboard.
  2. System validates the input is non-empty and under 50,000 characters.
  3. System generates a 384-dimensional embedding vector using Sentence-BERT.
  4. System stores the job description and its embedding in the job_descriptions table.
  5. System returns the job description ID with HTTP 201.
